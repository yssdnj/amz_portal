## 配置方案

沿用 `PORTAL_LOGIN_USERNAME`、`PORTAL_LOGIN_PASSWORD` 作为原主账号配置。新增可选 `PORTAL_EXTRA_USERS`，值是 JSON 对象：账号名到密码字符串的映射；缺少该项时保持只配置主账号的行为。

加载时拒绝非法 JSON、非对象、重复账号键、空账号或密码、非字符串值、与主账号重名的条目。不静默覆盖账号，不把配置内容或密码放进异常信息。空 JSON 对象合法，表示没有额外账号。

不更改已配置账号的大小写或自动裁剪账号名；账号输入与配置准确匹配。主账号和额外账号采用相同密码校验方式和通用失败提示。

选择配置扩展而不是用户数据库，是因为现有系统采用 `.env` 管理账号，用户仅要求新增账号，没有账号自助管理需求。

## 认证与身份兼容

每个账号的稳定 ID 都使用已实现的公式：

`str(uuid5(NAMESPACE_URL, "urn:amz-portal:user:" + username))`

原 `howgo` 的 ID 不变；`howgo04` 的 ID 与之不同。修改密码或重启不会改变账号 ID。账号改名视为新身份。

登录时只在账号和对应密码均验证成功后写入签名会话的 `authenticated=True`、`user_id`。用户名显示从服务端已配置账号映射反查，不信任客户端提交的身份头或 user_id。

建立统一的会话身份解析：authenticated 必须严格为 True，user_id 必须是当前配置中的某个账号 ID。首页、状态/控制 API、原 auth check 和身份接口使用同一验证规则。删除一个额外账号并重启后，其旧会话不再获得访问权限。

- `GET /api/auth/check` 继续有效会话 204、无效会话 401，无 JSON 身份内容。
- `GET /api/auth/user` 继续有效会话 200、仅返回 `{"user_id": "稳定ID"}`；失败 401；两种情况均 no-store，不增加 username 响应字段，保持 SP 接口契约。
- 当前已登录且具有原账号有效 user_id 的签名会话继续有效。
- 更早版本只含 authenticated=True、没有 user_id 的会话需要重新登录，不能将其默认映射给某个用户。此前测试允许旧会话通过 auth check，本次因多个账号消除该身份歧义，将对应兼容测试明确改为拒绝无身份会话。
- Cookie 名称、Path、12 小时有效期、HttpOnly、SameSite=Lax、Secure 和签名密钥保持现有设置。
- 退出清空浏览器会话。仍使用原签名会话机制，不引入服务端会话数据库。

两个账号目前都可使用已有的启动、暂停和 Linux 重启控制；没有角色分级。

## 当前用户显示

门户首页经过会话验证后，从服务端账号映射得到准确用户名，在顶部右侧显示。

使用 HTML 转义后插入文本，不将用户名作为 HTML 或 JavaScript 执行，不通过 localStorage 或 URL 参数恢复身份。主页不缓存，避免用户切换时出现另一账号的用户名。

用户名旁边依次放置主题按钮和退出按钮。桌面保持右侧对齐；手机时允许标题区调整排列，用户名单行省略并提供完整 title，不挤压两个图标按钮。显示 `howgo` 或 `howgo04`，不显示密码或用户 UUID。

## 明暗主题

沿用现有布局、模块图标、卡片顺序、状态标记和控制交互。把相关颜色集中为 CSS 变量，并给 light/dark 各一套语义颜色，覆盖背景、顶栏、标题、正文、卡片、边框、输入、按钮、状态和重启弹窗。

暗色保留现有暗色工作界面的辨识度，浅色采用冷白背景、白色内容面、深灰文字，运行/异常/开发中状态继续用蓝、红、金色区分。浅色须覆盖弹窗、禁用按钮和错误提示，不只切换 body 背景。

共用主题代码负责：

1. 在首次绘制前读取合法的 light/dark 存储值；未保存或非法值使用 dark。
2. 设置根元素 data-theme 和 color-scheme。
3. 按钮显示 Lucide 太阳/月亮图标，title 和 aria-label 表明将切换到的主题，支持键盘操作和可见焦点。
4. 点击立即切换并尝试保存。localStorage 不可用时仍能切换，不阻断登录或模块状态加载。
5. 同源其他标签页更改存储时同步主题。

只共享实际复用的主题变量、按钮和脚本，不拆分无关门户业务逻辑。不加入新的外部 CDN 请求。
