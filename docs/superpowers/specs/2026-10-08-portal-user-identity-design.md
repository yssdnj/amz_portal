# 门户用户身份校验接口设计

## 目的与范围

SP 项目需要按门户登录用户保存促销表格列宽，并让同一账号跨浏览器读取同一份偏好。门户只负责提供可信、稳定的用户身份；偏好数据库和表格交互由 SP 项目负责。

用户已确认采用 SP 后端携带原 Cookie 向门户查询身份的方式，前端继续通过现有门户登录并进入 SP 项目，不增加二次登录。

本次不扩展注册、多用户管理或权限系统，不保存列宽，不修改 SP 项目代码，不自动提交、推送或部署，不调用 Amazon SP-API。

## 已检查的现状

- `portal.py` 使用 Starlette `SessionMiddleware` 校验签名 Cookie。
- 登录成功后会话只包含 `authenticated=True`。
- Cookie 名称为 `amazon_portal_session`，Path 为 `/`，有效期 12 小时，HttpOnly、SameSite=Lax 和配置控制的 Secure 属性保持不变。
- `/api/auth/check` 有效登录返回 204，未登录返回 401。
- 退出清空浏览器会话。
- Nginx 的 `/amazon/official-sp/` 页面及 API 使用门户 auth_request，并默认转发原请求 Cookie。
- 网关 `/amazon/api/` 已代理到门户 `/api/`，新增接口无需修改 Nginx 路由。
- 门户首页代理可能将 Cookie Path 从 `/` 改写成 `/amazon/`，两种 Path 均覆盖 `/amazon/official-sp/`。

## 方案选择

1. **选定：SP 后端通过固定门户地址校验 Cookie。** 门户验证签名后返回用户 ID，SP 不需要门户签名密钥，且不依赖身份头。
2. Nginx 注入身份头：需要同时覆盖客户端同名头并建立后端可信代理验证，增加部署和安全约束，本次不采用。
3. SP 直接校验门户 Cookie：会共享签名密钥及会话格式，扩大耦合和密钥接触范围，本次不采用。

## 稳定用户 ID

使用标准库 UUID5 从已配置且完成密码验证的账号生成 ID：

`str(uuid5(NAMESPACE_URL, "urn:amz-portal:user:" + LOGIN_USERNAME))`

- ID 使用准确的账号字符串，不自行改变大小写或去除空格。
- 同一账号在不同浏览器、门户重启和修改密码后得到相同 ID。
- ID 不依赖密码或会话签名密钥。更换会话密钥会使旧 Cookie 失效，但重新登录后 ID 保持不变。
- 更改账号名称会产生新的 ID，本次不支持账号重命名后的偏好迁移。
- UUID 是偏好数据的账户索引，不是秘密或认证凭据。

登录通过现有账号、密码校验后，清空旧会话并写入 `authenticated=True` 和服务器生成的 `user_id`。不从登录请求额外字段或任何身份头取 ID。

## 接口契约

### `GET /api/auth/user`

SP 后端调用固定地址 `http://127.0.0.1:5000/api/auth/user`，请求仅需要携带浏览器原请求中的 Cookie。地址由 SP 服务端配置，不允许请求者指定。

成功条件：签名 Cookie 有效、会话未过期、`authenticated` 严格为 True，且会话中的 `user_id` 是当前配置账号对应的稳定 ID。

成功返回 HTTP 200，JSON 仅包含一个字符串字段：

```json
{"user_id": "60e76e67-2974-5b82-8fbd-54bd2ea6be8c"}
```

上面的 UUID 是示例账号 `example-user` 按上述公式得到的结果，实际值由已验证配置账号生成。

缺少 Cookie、签名无效、会话过期、缺少身份或身份与当前账号不符，均返回 HTTP 401 和现有未登录错误格式，不返回用户身份。

响应设置 `Cache-Control: no-store`，成功和失败均禁止身份响应缓存。响应体不得含账号密码、会话密钥、Cookie 或 token。中间件现有会话 Cookie 更新机制保持原状；SP 不把身份接口的 Set-Cookie 转发给浏览器。

接口忽略 `X-User-ID`、`X-Portal-User-ID`、`Authorization` 等未经门户会话验证的身份声明。

### 原接口兼容

`GET /api/auth/check` 继续按现有 authenticated 标志返回 204/401。旧版本签名会话仍可访问门户，但因没有 user_id，身份接口返回 401；用户重新登录一次后可保存账户偏好。其他模块接口和前端页面保持现有行为。

退出登录继续清空 Cookie；使用清空后的浏览器会话访问身份接口返回 401。本次沿用原有无服务端会话存储的机制，不新增会话撤销数据库，也不宣称已经使复制保存的旧签名 Cookie 立即失效。

## SP 接入方式

1. 用户从 HTTPS 网关登录门户并进入 `/amazon/official-sp/`。
2. 浏览器请求 SP 偏好 API，自动携带 HttpOnly 门户 Cookie，不需要前端读取 Cookie。
3. SP 后端从请求中取得 Cookie，向固定本机门户身份接口发送 GET。仅转发 Cookie，不使用客户端提供的 user_id 或身份头。
4. 门户返回 200 时，SP 严格校验响应结构，并仅使用返回的 user_id 查询或保存偏好。
5. 门户返回 401 时，不保存账户偏好；连接失败、超时、非 200 或响应格式错误时也不能信任客户端身份。SP 负责定义相应的失败提示或临时交互行为。

SP 必须禁止共享缓存或跨请求复用其他用户的身份结果。Cookie 不得写入日志。生产跨主机部署需要重新确定受保护的校验传输方式，本次固定为本机回环连接。

浏览器直连 `http://127.0.0.1:8015` 时，Secure Cookie 通常不会随 HTTP 请求发送，且外网域名 Cookie 不适用于 127.0.0.1。没有有效门户会话时，SP 允许临时调整列宽和排序，不保存至账户；不降低门户 Cookie 安全属性来支持直连。

## 修改文件与验收

- `portal.py`：生成稳定 ID、登录写入身份、新增只读接口。
- `tests/test_portal_login.py` 或独立身份测试文件：覆盖两套独立 Cookie 会话的 ID 一致性、未登录、无效签名、过期、缺少或错误身份、伪造身份头、退出和原 check 约定。
- `README.md`：记录服务端调用方式、旧会话重新登录、Cookie Path 和本地直连限制。
- 不修改 Nginx、密码、会话密钥、启动脚本或其他项目。

运行现有门户测试确认登录、控制接口和模块访问没有回归，并用隔离的本机运行实例实际执行双客户端登录、身份查询、无效会话和退出链路。测试仅使用专用测试凭据，避免输出真实密码、签名 Cookie 或密钥。完成后提供 SP 接入契约，不自动重启当前生产门户或部署云端。
